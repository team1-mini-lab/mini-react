# ADR-0004: Diff는 이전 dict를 가리키는 변경 목록만 만들고, Patch는 dict에 기억한 실제 노드(dom)로 그 변경을 적용한다. 자식은 key로 짝짓는다

## Context and Problem Statement

Patch를 하려면 먼저 무엇이 달라졌는지 알아야 합니다. 이전 Virtual DOM과 새 Virtual DOM을 비교해 달라진 노드와 그 종류를 찾고(Diff), 그 변경만 실제 영역에 반영해야(Patch) 합니다(FR-03~FR-06, NFR-01, C-03).

이 ADR은 네 가지를 정합니다.

1. Diff와 Patch를 나눌까, 합칠까?
2. 변경 목록에서 "어디를"(Patch가 고칠 실제 노드)을 어떻게 표현할까?
3. 자식 목록을 같은 자리끼리 짝지을까, 이름표(key)로 짝지을까?
4. key를 Virtual DOM dict의 어디에 둘까?

3번이 문제가 되는 이유는 이렇습니다. 장바구니 목록에서 사용자가 바나나 줄 입력칸에 "3"을 적은 뒤, 맨 앞에 사과 줄을 추가하고 Patch를 눌렀다고 합시다.

```
이전 children:  [ 바나나, 딸기 ]
새   children:  [ 사과, 바나나, 딸기 ]
```

같은 자리끼리 짝지으면 다음 두 문제가 생깁니다.

- **사용자 상태가 엉뚱한 줄로 간다**: 바나나 줄의 글자가 "사과"로 바뀌고 입력칸은 그대로라서 "3"이 사과 옆에 남는다(FR-04 위반).
- **바뀌지 않은 것까지 고친다**: 실제로 바뀐 건 1줄 추가인데 조작은 3번(글자 수정 2번 + 추가 1번) 일어난다. 목록이 100줄이면 101번이다(NFR-01 위반).

삭제(맨 앞 줄 지우기)와 순서 바꾸기에서도 똑같이 생깁니다. 원인은 앞에 무언가가 끼어들거나 빠지면 뒤쪽 자리 번호가 전부 밀리는데, 자리 비교는 그걸 내용이 바뀌었다고 착각하기 때문입니다.

## Decision Drivers

- **테스트 가능성**: Diff를 실제 DOM 없이 dict 두 개만으로 테스트할 수 있어야 한다.
- **읽기/쓰기 분리**: ADR-0003에서 정한 원칙과 일관되어야 한다. Diff = 읽기, Patch = 쓰기.
- **과제 문구**: "Diff를 구현하고 Patch한다"(C-03)와 맞아야 한다.
- **최소 변경과 사용자 상태 유지**: 바뀌지 않은 노드는 그대로 두고(FR-04, FR-05), 조작 횟수는 바뀐 부분 수에 비례해야 한다(NFR-01).
- **견고성**: 실제 영역에 주석이 있어도(ADR-0002), 여러 개를 한 번에 지워도 엉뚱한 노드를 고치지 않아야 한다(NFR-03).
- **일관성**: 성격이 다른 정보를 섞지 않는다(읽기/쓰기, Diff/Patch, 데이터/참조).

## Considered Options

**결정 1. Diff와 Patch**
- A. 나눈다: Diff가 비교만 해서 변경 목록을 만들어 돌려주고, Patch가 그 목록을 받아 실제 DOM에 적용한다.
- B. 합친다: 비교하는 함수가 다른 곳을 찾는 즉시 실제 DOM을 고친다.

**결정 2. "어디를"의 표현**
- 1. 경로: 루트부터 자리 번호를 나열한다(`[1, 2]`). 변경들은 납작한 list 하나에 담긴다.
- 2. 트리 모양: 변경 목록을 Virtual DOM과 같은 트리 모양으로 만들고, 각 노드 자리에 "이 노드의 변경 + 자식들의 변경"을 담는다.
- 3. 실제 노드를 dict에 기억: dict에 실제 노드를 가리키는 키를 하나 더 붙이고 Patch는 그걸 바로 쓴다.
  - 3+. 3을 조금 바꿔, 변경 목록은 실제 노드가 아니라 **이전 dict 객체**를 가리키게 한다.

**결정 3. 자식 짝짓기**
- 가. 같은 자리(번호)끼리 짝짓고, 목록 순서 문제는 알려진 한계로 둔다.
- 나. key를 지원한다. 자식은 "몇 번째냐"가 아니라 "누구냐"로 짝짓는다.

**결정 4. key 위치**
- A. `attrs` 안에 그대로 둔다.
- B. `key`라는 별도 키로 뺀다.

## Decision Outcome

Chosen options: **결정 1-A, 결정 2-3+, 결정 3-나, 결정 4-B**.

- **1-A**, because Diff를 실제 DOM 없이 dict 두 개만으로 테스트할 수 있어 실용적이고, 과제 문구(C-03)와 1:1로 맞으며, ADR-0003에서 정한 읽기/쓰기 분리 원칙과 일관되기 때문이다.
- **2-3+**, because 자리 번호로 찾지 않으므로 주석 때문에 자리가 어긋나는 문제(ADR-0002)와 여러 개 삭제 시 번호가 밀리는 문제가 사라지고, 변경 목록이 이전 dict를 가리키고 Diff는 `dom`을 읽지 않으므로 "Diff를 dict만으로 테스트한다"는 1-A의 핵심 이유도 지켜지기 때문이다. 또 리액트가 실제 노드를 어떻게 추적하는지 직접 겪어 볼 수 있다.
- **3-나**, because 목록 앞에 항목이 끼어들거나 순서가 바뀔 때 입력값이 엉뚱한 줄로 가는 문제(FR-04)와 조작 폭증(NFR-01)을 해결하고, 2-3+으로 실제 노드를 이미 잡고 있어 이동 구현이 쉽기 때문이다.
- **4-B**, because `key`는 화면에 영향이 없는 짝짓기용 정보이므로 화면용 데이터(`attrs`)와 분리하는 것이, 읽기/쓰기·Diff/Patch·데이터/참조를 분리한 지금까지의 결정과 일관되기 때문이다.

### 1. 노드 하나 비교하기

위에서부터 순서대로 조건을 확인한다. 조건에 해당하는 칸을 처음 만나면 그 칸의 변경으로 정하고, 그 아래 칸들은 확인하지 않는다.

| 순서 | 조건 | 변경 종류 | Patch가 할 일 | 자식 비교 |
|---|---|---|---|---|
| 1 | 이전엔 없고 새로 있음 | **추가** | `vdom_to_dom`으로 만들어 → 제자리에 `insertBefore` | ✗ |
| 2 | 이전엔 있고 새로 없음 | **삭제** | `dom.remove()` | ✗ |
| 3 | `type`이 다름 | **교체** | `vdom_to_dom`으로 만들어 → `dom.replaceWith` | ✗ |
| 4 | 둘 다 태그, `tag`가 다름 | **교체** | 3과 같음 | ✗ |
| 5 | 둘 다 글자, `text`가 다름 | **글자 수정** | `dom.nodeValue = 새 text` | ✗ (자식 없음) |
| 6 | 둘 다 태그, `tag` 같음, `attrs` 다름 | **속성 수정** | 생기거나 바뀐 속성 `setAttribute`, 사라진 속성 `removeAttribute`. `value`·`checked`는 지금 값(property)도 함께 바꾸되, 이미 같으면 건드리지 않는다 (2026-11-10 추가) | ○ |
| 7 | 위 어디에도 안 걸림 | 변경 없음 | 없음 | 태그면 ○ |
| + | 짝은 맞는데 자리가 다름 | **이동** | `insertBefore`로 제자리에 옮김 | 이동했는지와 상관없이 1~7번 결과를 따른다 |

- 노드의 **정체를 나타내는 키**(`type`, `tag`)가 다르면 교체하고, **내용을 나타내는 키**(`text`, `attrs`)만 다르면 수정한다.
  - `type`이 다르면 한쪽엔 `text`가, 다른 쪽엔 `tag`·`attrs`가 있어서 나머지 키는 비교 대상 자체가 없다. 그래서 `type`을 맨 처음 비교한다.
  - 브라우저에서 이미 만든 태그의 종류를 바꾸는 명령이 없으므로, `tag`가 다르면 새로 만들어 교체해야 한다(FR-06).
- 추가와 교체는 `vdom_to_dom`이 새 dict의 자식까지 통째로 만들고, 삭제는 `remove()`하면 자식도 함께 떨어져 나가므로 자식 비교가 필요 없다. **둘 다 태그 노드이고 `tag`가 같을 때만** 자식을 비교한다.
- 자식 비교는 **같은 비교 함수를 자식 쌍마다 다시 부른다**(재귀).
- 노드 하나 비교에서는 `key`를 보지 않는다. 짝이 정해졌다는 건 이미 key가 같다는 뜻이다.
- **변경 종류는 6가지**: 추가, 삭제, 교체, 글자 수정, 속성 수정, 이동. (TBD-03)
- **`value`·`checked` (2026-11-10 추가)**: 입력칸의 `value`와 체크박스의 `checked` 속성은 "처음 값"일 뿐이라, `setAttribute`만으로는 사용자가 이미 타이핑하거나 누른 **지금 값**이 바뀌지 않는다. 그래서 이 두 속성은 지금 값(`el.value`, `el.checked`)도 함께 바꾼다. 지금 값과 이미 같으면 건드리지 않는다. 같은 값을 다시 쓰면 커서가 끝으로 튈 수 있기 때문이다. Phase 2 Todo 앱에서 할 일을 추가한 뒤 입력칸을 비우거나(#44), 완료 체크를 상태와 맞출 때 필요하다. 이 브라우저 동작은 구현 때 테스트로 확인한다.

### 2. 자식 목록 짝짓기

| 규칙 | 내용 |
|---|---|
| key 있는 자식 | 이전 자식들로 **key 장부**(key → 이전 dict)를 만들고, 같은 key끼리 짝짓는다 |
| key 없는 자식 | **key 없는 자식끼리** 그들 사이의 순서대로 짝짓는다. 리액트처럼 "전체 자리 번호"를 숨은 key로 쓰면 앞에 key 있는 항목이 끼어들 때 key 없는 자식들이 다시 밀리기 때문이다 |
| 짝 없는 새 자식 | 추가 |
| 짝 없는 이전 자식 | 삭제 |
| 중복 key | 같은 부모 안에 같은 key가 2개 이상이면 콘솔에 경고하고, **그 부모의 자식 전체를 자리 비교**로 처리한다. 덮어쓰기로 노드가 사라지는 사고를 막는 가장 단순한 안전장치다 |
| 순서 맞추기 (단순한 방법) | 새 자식을 **앞에서부터** 하나씩 보면서, 해당 실제 노드가 **이미 그 자리에 있으면 그대로**, 아니면 `insertBefore`로 그 자리에 옮긴다. 결과 화면은 항상 정확하다. 필요 이상으로 옮길 수 있는 것은 알려진 한계다 |
| 추가 위치 | 추가도 순서 맞추기와 같은 방식으로 **제자리에** `insertBefore`로 넣는다. `appendChild`(끝에 붙이기)는 쓰지 않는다. key 방식에서는 추가가 맨 끝에만 생기지 않기 때문이다 |
| key가 바뀐 항목 | 다른 항목으로 보고 삭제 + 추가한다. **의도된 동작**이다. key가 다르면 다른 항목이라는 것이 key의 약속이다 |

> **ADR-0005에서 정했다 (A)**: Diff가 이전 트리의 dict 순서로 "이미 그 자리에 있는가"를 판단한다. 이동은 Diff의 변경 목록에 나타난다.

### 3. 변경 목록

Diff는 비교만 해서 변경 목록을 만들어 돌려주고, Patch가 그 목록을 받아 실제 DOM에 적용한다. 변경 하나에 담을 내용은 다음과 같다.

| 종류 | 담을 정보 |
|---|---|
| 추가 | 어디에(부모 위치), 새 dict |
| 삭제 | 어디를 |
| 교체 | 어디를, 새 dict |
| 글자 수정 | 어디를, 새 text |
| 속성 수정 | 어디를, 붙이거나 바꿀 속성들, 지울 속성 이름들 |
| 이동 | 대상, 부모, 기준 (ADR-0005) |

"어디를"·"어디에"는 실제 노드가 아니라 **이전 트리의 dict 객체**를 가리킨다.

```
Diff  : "이전 트리의 이 dict(객체)의 글자를 '딸기'로"   ← dict만 가리킴. 실제 노드는 안 봄
Patch : 그 dict의 dom 키를 꺼내 실제 노드를 얻고 → nodeValue = "딸기"
```

> **ADR-0005에서 정했다 (B)**: 추가·이동의 위치는 번호가 아니라 기준 dict(그 순간 그 자리에 있는 이전 dict, 없으면 끝)로 담는다.

> **ADR-0005에서 정했다 (C)**: 기록 형식(`kind` 6종)과 적용 순서(삭제 → 앞에서부터 [자리 맞추기 → 자신의 변경 → 자식] → 마지막에 `dom` 복사).

### 4. `dom` 규칙

| # | 규칙 | 이유 |
|---|---|---|
| 1 | 실제 노드를 가리키는 키 이름은 `dom` | 짧고 뜻이 분명함 |
| 2 | `dom`은 **실제 영역**의 노드만 가리킨다. 테스트 영역은 코드 입력칸(a3)과 미리보기(g1)로 다시 그린다(ADR-0006) | Patch(최소 변경)를 하는 곳이 실제 영역뿐 |
| 3 | `dom_to_vdom`은 실제 영역을 처음 변환할 때만 각 dict에 `dom`을 기록한다. 기록 여부는 호출하는 쪽이 정하고 기본은 기록 안 함 | 첫 Patch부터 `dom`이 있어야 함. 테스트 영역 노드가 기록되면 Patch가 엉뚱한 영역을 고침 |
| 4 | `vdom_to_dom`은 `dom`을 **읽지도 기록하지도 않는다** | 미리보기를 그릴 때도 쓰이므로, 기록하면 실제 영역을 가리키던 `dom`을 덮어씀 |
| 5 | Diff는 `dom`을 읽지도 비교하지도 않는다. 변경 목록은 **이전 dict 객체**를 가리킨다 | Diff를 dict만으로 테스트 |
| 6 | Patch가 끝나면: 그대로 둔 노드는 이전 dict의 `dom`을 새 dict에 **복사**하고, 추가·교체로 새로 만든 노드는 그 노드(자손 포함)를 새 dict들에 **기록**한다 | 다음 Patch 때 새 트리가 "이전 트리"가 되므로 |
| 7 | `dom`은 **지금 실제 영역에 그려진 트리**에서만 믿는다. State History에 저장된 다른 시점의 dict에 남은 `dom`은 의미가 없다 | 뒤로가기 때도 Diff의 "이전" 쪽은 언제나 지금 트리이므로 문제없음 |
| 8 | FR-01 인수 기준, ADR-0002 T10, ADR-0003 왕복 테스트는 `dom`을 비교하지 않는다 | 두 영역의 `dom`은 항상 달라서 깊은 비교가 늘 실패하므로 |

> **ADR-0005에서 정했다 (D)**: Diff는 `{ 변경 목록, 짝 목록 }`을 돌려준다. 짝 목록은 노드를 계속 쓰는 쌍만 담는다(교체 제외).

### 5. `key` 규칙

| # | 규칙 | 이유 |
|---|---|---|
| 1 | HTML에서는 `<li key="banana">`처럼 `key` 속성으로 적는다 | 리액트와 같은 이름. 브라우저는 모르는 속성도 그대로 보관하므로 동작에 문제없음 |
| 2 | `key`는 **태그 노드에만** 있는 선택 키다. 값은 문자열. 없으면 키 자체가 없다 | 글자 노드는 HTML에서 속성을 가질 수 없음 |
| 3 | `dom_to_vdom`은 HTML의 `key` 속성을 읽어 `key`에 넣고, **`attrs`에서는 뺀다** | 분리의 핵심. 속성 비교에 key가 섞이지 않음 |
| 4 | `vdom_to_dom`은 `key`가 있으면 **`key` 속성으로 다시 붙인다** | 안 붙이면 미리보기와, Patch가 추가·교체로 만든 실제 영역 노드에서 `key` 속성이 사라짐. 코드 입력칸의 `key`는 Virtual DOM → 코드 변환(ADR-0006 a3)이 따로 붙임 |
| 5 | Diff는 자식을 짝지을 때 `key`를 본다. 노드 하나 비교(1절 표)에서는 `key`를 보지 않는다 | 짝이 정해졌다는 건 이미 key가 같다는 뜻 |
| 6 | FR-01 비교 기준에는 `key`를 **넣지 않는다**. 단, ADR-0003 **왕복 테스트**에는 `key`를 **포함**한다 | key는 화면에 영향이 없으므로 "화면이 같은가"와 무관. 왕복 테스트는 규칙 4(다시 붙이기)를 빠뜨렸는지 잡아내는 유일한 테스트 |

### 6. 비교 기준

| 비교 | 보는 키 | 비교 목적 |
|---|---|---|
| FR-01 인수 기준, ADR-0002 T10 | 다섯 키 (`dom`, `key` 제외) | 화면이 같은가 |
| ADR-0003 왕복 테스트 | 다섯 키 + `key` (`dom` 제외) | 변환 함수가 정보를 잃지 않는가 |
| Diff | 다섯 키 + 짝지을 때 `key` (`dom`은 안 읽음) | 무엇이 바뀌었나 |

### 7. 알려진 한계 (이 프로젝트에서 해결하지 않음)

| 한계 | 이유 |
|---|---|
| 이동 횟수 최소화 안 함 | 결과 화면은 정확. 필요 이상으로 옮길 수 있음 |
| key 없는 노드(글자, 공백)가 끼어들 때 자리 밀림 | key가 없으면 순서로 짝지을 수밖에 없음. FR-04에 닿는 문제지만 비용 때문에 남김 |
| key가 바뀌면 삭제 + 추가 | 의도된 동작. key가 다르면 다른 항목이라는 약속 |

### Consequences

- Good, because Diff는 실제 DOM 없이 dict 두 개만으로 테스트할 수 있고, 변경 목록 개수로 "1개를 바꾸면 조작 1회"(NFR-01)를 바로 셀 수 있다.
- Good, because Diff = 읽기, Patch = 쓰기로 ADR-0003의 구분이 그대로 지켜진다.
- Good, because Patch가 `dom`으로 실제 노드를 바로 꺼내므로 주석 자리 문제(ADR-0002)와 여러 개 삭제 시 자리 밀림 문제가 생기지 않는다.
- Good, because key로 짝지으므로 목록 앞 추가·삭제·순서 변경에도 같은 항목은 같은 실제 노드를 쓰고 입력값과 커서가 따라간다(FR-04). 사과 1줄 추가는 목록 길이와 상관없이 조작 1번이다(NFR-01).
- Good, because 이동할 실제 노드를 `dom`으로 이미 잡고 있어 `insertBefore`로 바로 옮길 수 있다. 경로 방식이었다면 이동 중에 다른 노드들의 번호가 계속 바뀌어 훨씬 까다로웠다.
- Bad, because 경로 방식보다 할 일이 많다: ADR-0001 노드 모양 변경, Patch 후 `dom` 복사, State History·두 영역 규칙.
- Bad, because Patch 후 `dom` 복사를 하나라도 빠뜨리면 다음 Patch 때 `dom`이 없어서 오류가 난다.
- Bad, because 변경 종류가 과제 원문 [중점 포인트]의 5가지보다 하나 많은 6가지가 된다. key 지원은 과제가 요구하지 않지만 금지하지도 않는 추가 구현이다.
- Neutral, because `key` 분리로 `vdom_to_dom`에서 `key`를 다시 붙이는 일이 생긴다. 왕복 테스트에 `key`를 포함해 누락을 잡는다.

### Confirmation

- 구현 후 **`dom` 키가 없는 dict 두 개**로 Diff 테스트가 돌아가는지 확인한다. ("Diff는 dict만 가리킨다"는 설계 단계의 가설이므로 구현으로 확인해야 한다.)
- Diff 테스트는 "변경 목록이 **이전 트리의 그 dict를** 가리키는가"로 확인한다. 실제 DOM이 필요 없다.
- 코드 검토에서 Diff가 `dom`을 읽거나 비교하지 않는지 확인한다.
- 코드 검토에서 FR-01 비교와 ADR-0003 왕복 테스트가 **같은 비교 함수로 만들어지지 않았는지** 확인한다. 하나는 `key`를 빼고, 하나는 `key`를 넣는다.

> **ADR-0005에서 정했다 (E)**: Diff 테스트 D1~D15, Patch 테스트 P1~P12.

## Pros and Cons of the Options

### 결정 1

**A. 나눈다 (채택)**
- Good, because Diff를 실제 DOM 없이 dict 두 개만으로 테스트할 수 있고, 변경 목록 개수로 조작 횟수를 바로 셀 수 있다.
- Good, because ADR-0003의 읽기/쓰기 구분이 그대로 지켜진다.
- Good, because "Diff를 구현하고 Patch한다"는 과제 문구와 1:1로 맞다.
- Bad, because 변경 목록의 모양을 정해야 한다.

**B. 합친다**
- Good, because 즉시 실제 DOM을 고치므로 변경 목록 모양을 정할 필요가 없고 구조가 단순하다.
- Bad, because 실제 DOM이 있어야만 테스트할 수 있다.
- Bad, because 읽기와 쓰기가 한 함수에 섞이고, 하나의 함수가 Diff와 Patch를 둘 다 하게 된다.

### 결정 2

**1. 경로**
- Good, because 결과가 `[1, 2]` 같은 단순한 값이라 비교 테스트가 쉽고, 기존 ADR을 바꿀 필요가 없다. 구현 난이도가 낮다.
- Bad, because 번호를 셀 때 주석을 건너뛰어야 하고, Diff가 준 자리 번호로 실제 노드를 꺼내는 함수를 따로 만들어야 한다.
- Bad, because 앞에서 지우면 뒤 경로가 모두 밀리므로, 모든 경로를 먼저 실제 노드로 바꿔 둔 뒤 고쳐야 한다.

**2. 트리 모양**
- Good, because 기존 ADR을 바꿀 필요가 없고, 여러 개 삭제 시 한 부모 안에서만 순서를 주의하면 된다.
- Bad, because 번호를 셀 때 주석을 건너뛰어야 하고, 중첩 구조라 비교 테스트가 복잡하다.

**3+. 이전 dict를 가리키고 dict에 실제 노드 기억 (채택)**
- Good, because 번호를 쓰지 않으므로 주석 자리 문제가 생기지 않고, 노드를 직접 잡고 있어 여러 개 삭제에도 안전하다.
- Good, because Diff가 `dom`을 읽지 않으면 dict만으로 테스트할 수 있다.
- Good, because 실제 리액트와 가까운 방식이라 포트폴리오 설명거리가 된다.
- Bad, because ADR-0001 노드 모양을 바꿔야 하고, Patch 후 `dom` 복사, State History·두 영역 규칙이 추가로 필요하다. 구현 난이도가 높다.

### 결정 3

**가. 같은 자리끼리**
- Good, because 변경 종류가 과제 원문대로 5가지이고 구현이 단순하다.
- Bad, because 목록 앞 추가·삭제·순서 변경에서 사용자 상태가 엉뚱한 줄로 가고(FR-04), 조작이 목록 길이만큼 늘어난다(NFR-01).

**나. key 지원 (채택)**
- Good, because 같은 항목이 같은 실제 노드를 계속 써서 위 두 문제를 해결한다.
- Good, because 순서가 바뀌면 새로 만들지 않고 옮기므로 입력값과 커서가 노드와 함께 따라간다.
- Bad, because 변경 종류가 6가지로 늘고, key 없는 자식 규칙·중복 key 규칙이 필요하다.

### 결정 4

**A. `attrs` 안에 그대로**
- Good, because ADR-0001을 바꿀 필요가 없고, `vdom_to_dom`에서 다른 속성처럼 붙어 추가 작업이 없다.
- Bad, because 화면에 영향이 없는 짝짓기용 정보가 화면용 속성과 섞인다.
- Bad, because 속성 수정 비교에서 key를 빼야 한다. 잊으면 key 차이를 속성 수정으로 착각한다.

**B. 별도 키 (채택)**
- Good, because 화면용 데이터와 짝짓기용 정보가 분리되고, 속성 비교는 지금 방식 그대로 하면 된다.
- Good, because Phase 2에서 컴포넌트가 실제 리액트처럼 `key`를 따로 적는다.
- Bad, because ADR-0001에 `key`를 추가해야 하고, `vdom_to_dom`에서 key를 다시 붙이는 것을 잊으면 안 된다.
