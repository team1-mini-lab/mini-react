# ADR-0006: 테스트 영역은 HTML 코드 입력칸(원본)과 그 코드를 Virtual DOM을 거쳐 그린 미리보기로 구성한다

## Context and Problem Statement

Patch 버튼을 누르면 이렇게 진행됩니다.

```
① 테스트 영역 → 새 Virtual DOM          ← 이 ADR이 정하는 부분
② Diff(이전, 새) → { changes, pairs }   ← ADR-0004, ADR-0005
③ Patch → 실제 영역 반영                 ← ADR-0005
```

①을 정하려면 먼저 **사용자가 테스트 영역을 어떻게 고치는지** 정해야 합니다(TBD-02). 그런데 과제 원문은 두 방향으로 읽힙니다.

| 원문 | 가리키는 방향 |
|---|---|
| "사용자가 테스트 영역에 있는 샘플 **HTML 코드**를 자유롭게 수정합니다" | 코드를 타이핑해 고친다 |
| "방금 만든 Virtual DOM을 이용하여 테스트 영역을 **렌더링**합니다" | 테스트 영역은 그려진 화면이다 |
| "**실제 영역**의 샘플 **HTML 코드**를 Virtual DOM 트리로 변환합니다" | 그려진 실제 영역도 "HTML 코드"라고 부르므로, 단어 하나로는 정할 수 없다 |

또 FR-02의 인수 기준은 "태그, 속성, 글자의 추가·삭제·변경이 모두 가능하다"입니다.

## Decision Drivers

- **원문의 두 해석 충족**: "HTML 코드를 수정"과 "테스트 영역을 렌더링"을 모두 만족한다.
- **FR-02**: 태그, 속성, 글자를 모두 고칠 수 있어야 한다.
- **단방향 데이터 흐름**: 리액트의 원칙과 지금까지의 설계 원칙(한 방향, 원본 하나, 성격이 다른 것을 섞지 않음)을 따른다.
- **최소 변경**: 고친 것 없이 Patch하면 변경이 0개여야 한다(FR-04, NFR-01).
- **기존 결정 유지**: ADR-0002(공백 규칙)와 ADR-0003(Virtual DOM으로 그리기)을 그대로 쓴다.
- **도전과 완성도**: 포트폴리오 수준을 목표로 한다(NFR-04, 측정 기준은 TBD-06).

## Considered Options

**1. 테스트 영역 구성**
- 방법 1. HTML 코드 입력칸만
- 방법 2. 그려진 화면만 (화면에서 바로 고침)
- 방법 3. 코드 입력칸 + 그 코드를 그린 미리보기

**f. 무엇이 원본인가**
- f1. 코드가 원본, 미리보기는 보기 전용
- f2. 둘 다 고칠 수 있고 서로 맞춘다

**e. 미리보기를 언제 다시 그릴까**
- e1. 타이핑할 때마다
- e2. 버튼을 누를 때만
- e3. 타이핑이 잠시 멈추면 (debounce)

**a. Virtual DOM → 코드의 모양**
- a1. 있는 그대로 (공백 노드는 `" "` 한 칸)
- a2. 항상 보기 좋게 줄바꿈·들여쓰기
- a3. 원래 공백 노드가 있던 자리에서만 줄바꿈·들여쓰기

**c. 잘못된 HTML 입력**
- c1. 브라우저가 고쳐 읽은 결과를 그대로 받아들인다
- c2. 고쳐졌으면 경고만 한다
- c3. 고쳐졌으면 Patch를 막는다

**g. 미리보기를 무엇으로 그릴까**
- g1. Virtual DOM을 거쳐서: 코드 → 브라우저가 읽음 → `dom_to_vdom` → `vdom_to_dom`
- g2. 코드를 바로: 코드 → 브라우저가 읽음 → 미리보기

**h. 코드에 루트 태그까지 보여 줄까**
- h1. 루트까지 보여 준다
- h2. 루트의 자식만 보여 준다

**i. 중복 `id`**
- i1. 허용하고 규칙으로 관리한다 (영역은 틀로 찾는다)
- i2. 미리보기를 격리된 공간(Shadow DOM, iframe)에 그린다

## Decision Outcome

Chosen options: **방법 3, f1, e3, a3, c1, g1, h1, i1**.

- **방법 3**, because 도전하고 싶고, LMS 원문의 두 해석을 모두 충족하며, 포트폴리오 수준을 목표로 하기 때문이다.
- **f1**, because 미니라고 해도 리액트를 만드는 것이므로 리액트의 단방향 데이터 흐름 원칙을 따르고, 지금까지의 설계 원칙에도 위배되지 않기 때문이다.
- **e3**, because e2처럼 코드와 미리보기가 다른 순간이 있는 것은 사용자 경험상 좋지 않고, e1보다 쓰다 만 코드로 미리보기가 덜 깨져 보이기 때문이다.
- **a3**, because 고친 것 없이 Patch하면 변경이 0개가 되는 안정성이 FR-04, NFR-01과 직결되고, 새 규칙을 만들지 않고 ADR-0002의 공백 규칙을 그대로 이용하기 때문이다.
- **c1**, because e3 덕분에 미리보기로 바로 확인할 수 있고, 추가로 정할 것이 없으며, 지금까지의 설계와 일관되고, 브라우저는 잘못된 HTML에 오류를 내지 않는다는 전제와 맞기 때문이다.
- **g1**, because ADR-0003과 과제 원문("Virtual DOM을 이용하여 테스트 영역을 렌더링")을 그대로 만족하기 때문이다.
- **h1**, because 새 규칙이 필요 없고 기존에 결정한 코드 ↔ Virtual DOM ↔ 미리보기 흐름을 깨지 않기 때문이다.
- **i1**, because HTML 규칙을 어기게 되더라도 예외 규칙으로 관리할 수 있기 때문이다.
- 시연 기능(8절, 2026-11-10 추가)의 결정과 이유는 8절에 적는다.

### 1. 테스트 영역 구성과 데이터 흐름

```
┌─ 테스트 영역 ─────────────────────────────┐
│ ┌─ 코드 입력칸 (원본) ─────────────────┐  │  ← 사용자는 여기서만 고친다
│ └─────────────────────────────────────┘  │
│ ┌─ 미리보기 (보기 전용) ───────────────┐  │  ← 코드를 그린 결과
│ └─────────────────────────────────────┘  │
└──────────────────────────────────────────┘
```

```
                  ┌──────── a3 (Virtual DOM → 코드) ────────┐
                  │                                         ▼
           Virtual DOM                                 코드 입력칸  ← 사용자가 고침
                  ▲                                         │
                  └──── g1 (코드 → 읽기 → dom_to_vdom) ─────┘
                  │
                  ▼
             미리보기 (vdom_to_dom)
```

| 언제 | 흐름 |
|---|---|
| 첫 로드 | 실제 영역 → `dom_to_vdom`(기록함) → Virtual DOM → a3 → 코드 입력칸 → g1 → 미리보기 |
| 코드를 고침 | 입력이 멈추면(e3) 코드 → g1 → 미리보기 |
| Patch | 코드 → g1 → 새 Virtual DOM → 미리보기를 즉시 다시 그림 → Diff(이전, 새) → Patch |
| 뒤로·앞으로가기 | 기록의 Virtual DOM → `Diff(지금 트리, 기록 트리)` → Patch로 실제 영역 반영 → a3 → 코드 입력칸 → g1 → 미리보기 (ADR-0008 2절) |

- Patch가 읽는 것은 **원본인 코드**다. 미리보기는 잠깐 옛 모습일 수 있으므로(e3) 읽지 않는다.

### 2. 코드 → Virtual DOM (g1)

| 규칙 | 이유 |
|---|---|
| 코드를 `<template>` 요소에 넣어 브라우저가 HTML로 읽게 한다 | 화면에 붙지 않은 곳에서 읽으므로 미리보기 전에 그려지지 않고, 중복 `id`를 하나 더 만들지 않는다 |
| 읽은 결과의 첫 요소(루트)를 `dom_to_vdom`(기본 모드, `dom` 기록 안 함)으로 바꾼다 | 테스트 영역 쪽 노드가 `dom`에 들어가면 Patch가 엉뚱한 영역을 고친다(ADR-0002, `dom` 규칙 3) |
| 미리보기는 그 Virtual DOM을 `vdom_to_dom`으로 그린다 | ADR-0003 그대로. 미리보기가 Diff·Patch가 실제로 쓸 내용을 그대로 보여 준다 |

- `<template>`로 읽는 방법은 트레이드오프가 거의 없는 기계적인 결정으로, 설계 대화에서 제안되어 채택했다.

### 3. Virtual DOM → 코드 (a3)

| 규칙 | 이유 |
|---|---|
| 공백 노드(`" "`)가 **원래 있던 자리만** 줄바꿈 + 들여쓰기로 바꾼다. 없던 자리는 붙여 쓴다 | 공백 규칙은 "공백 덩어리 → 한 칸"이므로, `" "`를 `"\n  "`로 바꿔도 다시 읽으면 `" "`로 돌아온다. 고친 것 없이 Patch하면 변경 0개 |
| `<pre>` 안은 바꾸지 않는다 | ADR-0002의 `<pre>` 예외와 같은 이유. `<pre>` 안의 공백은 화면에 그대로 보인다 |
| 글자의 `<`, `&`는 `&lt;`, `&amp;`로 바꿔 적는다 | 그대로 적으면 브라우저가 `<`를 태그의 시작으로 읽어 내용이 바뀐다 |
| 속성 값의 `"`는 `&quot;`로 바꿔 적는다 | 그대로 적으면 `"`에서 속성 값이 끝난 것으로 읽힌다 |
| `key`가 있으면 `key` 속성으로 적는다 | 원본이 코드이므로, 빠지면 코드를 다시 읽은 새 Virtual DOM에도 `key`가 없어 Diff의 key 짝짓기가 깨진다 |
| `<br>`, `<img>`처럼 닫는 태그가 없는 태그는 닫는 태그를 쓰지 않는다 | 원래 닫는 태그가 없는 태그라, 써 넣으면 브라우저가 다르게 읽을 수 있다 |
| 들여쓰기 한 단계는 공백 2칸 | a3에서 공백은 다시 `" "` 한 칸이 되므로 보이는 모양에만 영향이 있다. ADR-0002 T2 예시와 맞춘 값 |

- 표의 아래 다섯 규칙은 트레이드오프가 거의 없는 기계적인 결정으로, 설계 대화에서 제안되어 채택했다.

### 4. 미리보기 갱신 (e3)

- 코드 입력이 **0.3초** 멈추면 미리보기를 다시 그린다. 0.3초는 시작 값이고, 써 보고 조정한다.
- 기다리는 중에 Patch를 누르면 미리보기도 **즉시** 다시 그린다. Patch가 끝난 순간에는 코드, 미리보기, 실제 영역이 모두 같은 모습이어야 하기 때문이다.
- 미리보기는 실제 영역이 아니므로 통째로 다시 그려도 FR-04에 어긋나지 않는다. FR-04는 Patch로 실제 영역을 고칠 때의 요구사항이다.

### 5. 잘못된 HTML (c1)

브라우저는 잘못된 HTML에 오류를 내지 않고, 정해진 규칙대로 고쳐서 읽는다.

| 입력 | 브라우저가 읽은 결과 |
|---|---|
| `<ul><li>사과<li>바나나</ul>` | `</li>`를 알아서 닫음 |
| `<p>안녕</div>` | 짝 없는 `</div>`를 무시함 |
| `<p>안녕<div>세상</div></p>` | `<p>`를 먼저 닫고 `<div>`를 밖으로 꺼냄 |

시스템은 고쳐 읽은 결과를 그대로 미리보기와 Patch에 쓴다. 사용자는 Patch 전에 미리보기로 확인한다.

### 6. 루트와 틀 (h1)

- 코드 입력칸에는 루트(`<div id="app">…</div>`)까지 보여 준다. 사용자가 루트를 고치면 루트도 Diff·Patch 대상이다(예: `div` → `section`이면 교체).
- 페이지는 실제 영역과 미리보기를 루트의 `id`가 아니라 **페이지가 만든 틀**로 찾는다. 루트 = 틀의 첫 자식 요소.

```html
<section id="real-area">   ← 페이지가 만든 틀 (고정)
  <div id="app">…</div>    ← 샘플의 루트 (Patch로 교체될 수 있음)
</section>

<section id="preview">     ← 미리보기 틀 (고정)
  <div id="app">…</div>
</section>
```

- 루트가 교체되어도 틀은 그대로라서, 다음에도 같은 방법으로 새 루트를 찾는다. 새 루트의 `dom`은 ADR-0005 F1이 기록한다.

### 7. 중복 `id` (i1)

실제 영역과 미리보기는 같은 모습이 되는 것이 목표(FR-01)이므로, 샘플 안의 모든 `id`는 항상 두 개씩 생긴다.

| 규칙 | 이유 |
|---|---|
| 페이지 코드는 샘플 안의 `id`로 요소를 찾지 않는다. 영역은 틀로 찾는다 | `getElementById`는 같은 `id` 중 문서에서 먼저 나오는 하나만 돌려주므로, 실제 영역 대신 미리보기 요소를 찾을 수 있다 |

**알려진 한계**: 이 규칙은 페이지 코드만 묶는다. 브라우저가 `id`를 쓰는 기본 기능(`<label for>`, `<a href="#...">`)은 막을 수 없어서, 샘플에 이런 기능이 있으면 실제 영역과 미리보기 중 한쪽만 동작한다. 샘플에는 이런 기능을 쓰지 않는 것을 전제로 한다.

### 8. 시연 기능 (2026-11-10 추가)

검증 페이지(#27)와 Phase 2 Todo 앱(#44) 검토에서 정한 화면 기능이다.

**결정**

| 결정 | 내용 | 이유 |
|---|---|---|
| 추가 구현 | Patch 하이라이트와 트리 보기를 넣는다 (SDD 부록 C 1·4번). 통째 교체 비교, 타임머신 슬라이더는 넣지 않는다 | 하이라이트: Patch가 이미 바뀐 노드의 `dom`을 알고 있어 붙이기 쉬우므로, 적은 비용으로 차별화할 수 있다 |
| 트리 보기의 내용 | **v2**: 이전 트리와 새 트리를 나란히 보여 주고, 각 트리에서 바뀐 노드를 색칠한다 | 과제 중점 포인트 "Diff 알고리즘 동작 방식"을 보여 주기 좋다. 새 트리 하나(v1)로는 `remove`를 보여 줄 수 없다 |
| 트리 보기의 모양 | **w1**: 들여쓰기 글자 목록(폴더 구조 모양) | UI가 중요한 과제가 아니다. 상자와 선 그림(w2)은 배치 계산과 넘칠 때 처리가 더 필요하다 |
| 하이라이트 적용 범위 | **y2**: Phase 1 검증 페이지와 Phase 2 Todo 앱 모두. Todo 앱에서는 입력칸을 강조하지 않는다 | 과제 최종 결과물("부분 업데이트되는 웹 페이지")에서 부분 업데이트가 눈에 보인다. 타이핑할 때마다 입력칸이 반짝이면 산만하다 |

**8-1. Patch 로그 요약**

`changes`의 `target`·`parent`·`before`는 dict 객체를 가리키므로(ADR-0004·0005) JSON으로 보여 주면 트리 전체가 쏟아진다. 기록마다 dict의 `tag`, `key`, `text`만 꺼내 요약 한 줄로 보여 준다. Phase 2 Todo 앱의 `DebugPanel`도 같은 형식을 쓴다.

| `kind` | 로그 표시 예 |
|---|---|
| `text` | `글자 수정: <li> "사과" → "딸기"` |
| `attrs` | `속성 수정: <p> class="red" 추가` |
| `add` | `추가: <li key="a"> (<li key="b"> 앞)` |
| `remove` | `삭제: <li key="c">` |
| `replace` | `교체: <p> → <h1>` |
| `move` | `이동: <li key="b"> (<li key="a"> 앞으로)` |

**8-2. 상태 문구**

버튼 옆에 상태 문구 한 줄을 둔다. 브라우저 알림 창(`alert`)은 페이지를 멈추게 해서 쓰지 않는다.

| 상황 | 문구 | 근거 |
|---|---|---|
| 바뀐 것 없이 Patch | 변경 사항 없음 | ADR-0008 k1 |
| Patch하지 않은 수정이 있어 이동 버튼이 꺼짐 | Patch하거나 수정을 되돌리면 이동할 수 있습니다 | ADR-0008 m3 |
| Patch 실패 후 복구 | 오류가 나서 실제 영역을 다시 그렸습니다 | ADR-0005 6절 |

**8-3. Patch 하이라이트**

| 규칙 | 이유 |
|---|---|
| Patch 쪽 공통 기능으로 두고, 페이지마다 켜고 끈다. 켤 때 **강조하지 않을 태그 목록**을 함께 받는다 | y2. Phase 1과 Phase 2가 같은 Patch를 쓴다(C-08) |
| Phase 1 검증 페이지는 아무 태그도 빼지 않는다. Phase 2 Todo 앱은 `<input>`, `<textarea>`를 뺀다 | Phase 1에서 입력칸이 바뀌는 것은 코드를 고친 결과라 보여 주는 게 맞다. Phase 2에서는 타이핑마다 다시 그려진다 |
| Patch가 끝난 뒤, `add`·`replace`의 새 노드, `text`·`attrs`·`move`의 대상 노드를 0.6초 동안 강조한다 | Patch가 바뀐 노드의 `dom`을 이미 알고 있다 |
| 글자 노드는 부모 요소를 강조한다 | 글자 노드에는 스타일을 줄 수 없다 |
| `remove`는 강조하지 않는다. Patch 로그에만 남는다 | 사라진 노드라 강조할 대상이 없다 |
| 강조는 요소의 속성(`class`, `style`)을 바꾸지 않는 방법(`element.animate()`)으로 한다 | 속성을 바꾸면 NFR-01·P3의 조작 횟수 측정에 섞이고, 실제 영역 DOM이 Virtual DOM과 잠시 달라진다. `element.animate()`가 속성을 바꾸지 않는다는 점은 HL2로 확인한다 |

**8-4. 트리 보기 (Phase 1 검증 페이지)**

| 규칙 | 이유 |
|---|---|
| Patch할 때마다 이전 트리(왼쪽)와 새 트리(오른쪽)를 들여쓰기 글자 목록으로 다시 그린다 | v2, w1. 보조 화면이라 통째로 다시 그려도 FR-04와 상관없다 |
| 한 줄에 `tag`, `key`, `attrs`, 글자 노드의 `text`를 보여 주고 `dom`·`events`는 보여 주지 않는다 | 화면 데이터가 아니다(ADR-0001 키의 무리) |
| 종류마다 다른 색을 쓰고 범례를 둔다. 새 트리의 짝 노드는 `pairs`로 찾는다 | `kind`별로 보이는 쪽이 다르다 |

| `kind` | 이전 트리 (왼쪽) | 새 트리 (오른쪽) |
|---|---|---|
| `remove` | 대상 색칠 | — |
| `add` | — | 새 노드 색칠 |
| `replace` | 옛 노드 색칠 | 새 노드 색칠 |
| `text`·`attrs` | 대상 색칠 | 짝 노드 색칠 |
| `move` | 대상 색칠 | 짝 노드 색칠 |

### Consequences

- Good, because 원문의 "HTML 코드를 수정"과 "테스트 영역을 렌더링"을 둘 다 글자 그대로 만족한다.
- Good, because 코드로 태그, 속성, 글자, `key`, 순서를 모두 고칠 수 있어 FR-02를 만족하고, D·P 테스트 상황을 화면에서 재현할 수 있다.
- Good, because 원본이 코드 하나이고 흐름이 한 방향이라, 두 원본을 맞추는 문제가 없다.
- Good, because 미리보기가 Virtual DOM을 거쳐 그려지므로 "Patch하면 실제 영역이 이렇게 된다"를 정확히 보여 준다.
- Good, because a3 덕분에 고친 것 없이 Patch하면 변경이 0개다.
- Good, because ADR-0002의 공백 규칙과 ADR-0003의 `vdom_to_dom`을 그대로 쓴다.
- Bad, because 테스트 영역에 화면이 하나 더 생기고, Virtual DOM → 코드 변환(a3)이라는 새 함수가 필요하다.
- Bad, because e3은 시간이 들어간 동작이라 테스트가 까다롭다. 실제로 기다리거나 시간을 흉내 내는 도구가 필요하다.
- Bad, because 사용자가 루트를 고칠 수 있어 루트 자체가 교체될 수 있다. 틀로 찾기로 대응한다.
- Bad, because 페이지에 같은 `id`가 두 개씩 생겨 HTML 규칙을 어긴다. `id`에 기대는 브라우저 기능은 한쪽만 동작한다(알려진 한계).
- Neutral, because 잘못된 HTML은 오류 없이 고쳐 읽히므로, 사용자가 의도와 다른 결과를 미리보기로 직접 확인해야 한다.

## Pros and Cons of the Options

### 1. 테스트 영역 구성

**방법 1. 코드 입력칸만**
- Good, because FR-02를 그대로 만족한다.
- Bad, because 테스트 영역이 그려진 화면이 아니게 되어 ADR-0003과 FR-01의 비교 대상을 다시 정해야 한다.

**방법 2. 그려진 화면만**
- Good, because 기존 `dom_to_vdom`을 그대로 쓰고, 사용자에게 직관적이다.
- Bad, because 기본으로는 글자만 고칠 수 있어, FR-02를 만족하려면 태그·속성을 고치는 별도 도구가 필요하다.

**방법 3. 코드 입력칸 + 미리보기 (채택)**
- Good, because 원문의 두 해석과 FR-02를 모두 만족한다.
- Bad, because 갱신 시점(e), 원본(f) 같은 결정이 더 필요하다.

### f

**f1. 코드가 원본 (채택)**
- Good, because 원본이 하나이고 흐름이 한 방향이다(리액트의 단방향 데이터 흐름).
- Good, because 나중에 f2로 확장할 때 반대 방향 흐름을 **더하기만** 하면 된다.
- Bad, because 글자 하나를 고칠 때도 코드를 찾아야 한다.

**f2. 둘 다 고침**
- Good, because 화면에서 바로 고칠 수 있어 편하다.
- Bad, because 원본이 둘이라 어느 쪽을 따를지 규칙, 커서가 튀는 문제, 서로가 서로를 계속 다시 그리는 문제를 정해야 한다.

### e

**e1. 타이핑할 때마다**
- Good, because 추가로 정할 것이 없다.
- Bad, because 쓰다 만 코드(`<li`)도 그려져 미리보기가 깨져 보인다.

**e2. 버튼을 누를 때만**
- Bad, because 버튼을 누르기 전까지 코드와 미리보기가 다르다.

**e3. 잠시 멈추면 (채택)**
- Good, because 거의 바로 보이고, 쓰다 만 코드로 덜 깨진다.
- Bad, because 기다리는 시간을 정해야 하고, 시간 테스트가 까다롭다.

### a

**a1. 있는 그대로**
- Good, because 고친 것 없이 Patch하면 변경 0개다.
- Bad, because 길어지면 한 줄이 매우 길어진다.

**a2. 항상 보기 좋게**
- Good, because 가장 읽기 쉽다.
- Bad, because 없던 자리에 공백 노드가 생겨 고친 것 없이 Patch해도 가짜 변경이 생긴다. 막으려면 ADR-0002를 다시 열어야 한다.

**a3. 원래 공백 자리만 (채택)**
- Good, because 고친 것 없이 Patch하면 변경 0개이고, 샘플이 들여쓰기돼 있으면 읽기도 좋다.
- Bad, because `<pre>` 안을 따로 처리해야 한다.

### c

**c1. 고친 대로 받아들임 (채택)**
- Good, because 추가로 정할 것이 없고, 미리보기가 확인 수단이 된다.
- Bad, because 사용자가 미리보기를 보지 않으면 의도와 다른 결과를 모를 수 있다.

**c2. 경고만 / c3. Patch를 막음**
- Good, because 시스템이 확인을 대신해 준다.
- Bad, because "고쳐졌다"를 감지하려면 입력 코드와 읽은 결과를 비교해야 하는데, 따옴표 모양·대문자·공백 차이까지 걸러야 해서 잘못된 경고가 나기 쉽다.

### g

**g1. Virtual DOM을 거쳐서 (채택)**
- Good, because ADR-0003과 과제 원문 그대로이고, 미리보기가 Diff·Patch가 쓸 내용을 정확히 보여 준다.
- Bad, because 미리보기를 그릴 때마다 변환을 두 번 더 한다(0.3초마다 한 번이라 부담은 작다).

**g2. 코드를 바로**
- Good, because 변환이 적다.
- Bad, because ADR-0003을 고쳐야 하고, 미리보기와 Patch 결과가 주석·공백에서 달라 보일 수 있다.

### h

**h1. 루트까지 (채택)**
- Good, because 코드 ↔ Virtual DOM 변환에 새 규칙이 필요 없다.
- Bad, because 루트가 교체될 수 있고, 루트의 `id`가 중복된다(틀로 찾기, i1로 대응).

**h2. 루트의 자식만**
- Good, because 루트를 고칠 수 없어 루트 교체가 없다.
- Bad, because 코드 → Virtual DOM, Virtual DOM → 코드 양쪽에 루트를 빼고 붙이는 규칙이 하나씩 필요하다.

### i

**i1. 허용 + 규칙 (채택)**
- Good, because 새 결정이 없고 FR-01의 화면 맞추기 문제가 생기지 않는다.
- Bad, because HTML 규칙을 어기고, `id`에 기대는 브라우저 기능은 한쪽만 동작한다.

**i2. 격리 (Shadow DOM, iframe)**
- Good, because HTML 규칙을 지키고, 페이지 CSS가 미리보기 안으로 새어 들어가지 않는다.
- Bad, because 바깥 CSS가 미리보기 안에 적용되지 않아 두 영역의 모습이 달라질 수 있고, 격리 방식 선택·CSS 맞추기·ADR-0003 수정이 필요하다.
