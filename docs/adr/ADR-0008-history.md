# ADR-0008: State History는 한 줄 기록 + 지금 위치로 관리한다. 뒤로 간 뒤 새로 Patch하면 뒤의 기록을 지우고, 변경 없는 Patch는 기록하지 않으며, Patch하지 않은 수정이 있으면 이동 버튼을 끈다

## Context and Problem Statement

과제 원문은 "새로 변경된 Virtual DOM은 State History에 저장한다", "뒤로가기, 앞으로가기 버튼을 눌러 State History에 저장된 특정 Virtual DOM으로 이동하며 실제 영역, 테스트 영역도 함께 변경되어야 한다"이다(FR-07, FR-08). 이를 위해 다음을 정해야 한다.

1. **분기 (TBD-01)**: Patch 세 번으로 기록이 A → B → C가 된 뒤 뒤로가기 두 번으로 A에 돌아가 새로 Patch해서 D가 생기면, B와 C는 어떻게 할까?
2. **변경 없는 Patch**: 고친 것이 없어 `changes`가 0개인 Patch도 기록할까?
3. **Patch하지 않은 수정**: 코드 입력칸을 고치고 Patch하지 않은 채 뒤로·앞으로가기를 누르면, 코드 입력칸이 기록 내용으로 덮여 고친 내용이 사라진다. 어떻게 할까?

## Decision Drivers

- **요구사항 범위**: FR-07·FR-08과 과제 원문은 이전·다음 시점 이동만 요구한다.
- **일정**: 팀 마감(11/11)까지 Phase 2 설계와 구현이 남아 있다.
- **사용자 경험**: 버튼이 고장 난 것처럼 보이거나, 고친 내용을 경고 없이 잃지 않아야 한다.
- **기존 결정과의 일관성**: ADR-0004 `dom` 규칙 7, ADR-0006(a3·g1·e3)과 맞아야 한다.

## Considered Options

**1. 분기**
- j1. 지운다: 지금 위치보다 뒤의 기록을 지운다. 기록은 list 하나 + 지금 위치 하나.
- j2. 남긴다: 가지 친 기록(트리)으로 보관한다.

**2. 변경 없는 Patch**
- k1. 기록하지 않고 "변경 사항 없음"을 알린다.
- k2. 기록한다.

**3. Patch하지 않은 수정이 있을 때 뒤로·앞으로가기**
- m1. 그냥 덮어쓴다.
- m2. 확인을 받는다.
- m3. 수정이 있으면 뒤로·앞으로가기 버튼을 끈다.

## Decision Outcome

Chosen options: **j1, k1, m3**.

- **j1**, because 가지 친 기록(j2)은 앞으로가기 규칙, 다른 갈래로 가는 화면, 기록 표시 방법을 새로 정해야 해서 지금 일정에 현실적으로 무리이고, 과제 요구사항도 이전·다음 시점 이동만 요구하기 때문이다. j1 → j2 확장은 History 모듈 안에서 끝나고 Diff·Patch는 건드리지 않는다.
- **k1**, because 기록하면 뒤로가기를 눌러도 화면이 안 바뀌는 칸이 생겨 버튼이 고장 난 것처럼 보이고, j1 때문에 바뀐 것이 없는데도 앞쪽 기록을 잃기 때문이다.
- **m3**, because 그냥 덮어쓰기(m1)와 달리 실수로 고친 내용을 잃는 일 자체를 막고, 확인을 받기(m2)와 달리 확인 화면과 확인을 기다리는 동안의 조작 규칙이 필요 없기 때문이다. 또 "Patch하지 않은 수정이 있다"를 Virtual DOM 비교로 판단하면 k1과 같은 기준이 되고, e3이 미리보기를 위해 이미 만드는 새 트리를 재사용하므로 추가 비용이 작다.

### 1. 기록의 모양

- 기록은 Virtual DOM 트리의 list 하나와 지금 위치 하나다.
- 첫 로드 상태를 0번 기록으로 둔다. Patch를 n번 하면(변경 없는 Patch 제외) 기록은 n+1개다.
- 기록에 저장된 dict의 화면 데이터(`type`, `tag`, `attrs`, `text`, `children`)와 `key`는 수정하지 않는다. `dom`은 지금 실제 영역에 그려진 트리에서만 믿는다(ADR-0004 `dom` 규칙 7). 뒤로·앞으로가기로 기록의 트리가 지금 트리가 되면 Patch가 그 dict들에 `dom`을 써 넣는데(ADR-0005 D1·F1), 이것이 맞는 동작이다.
- History는 DOM을 모르는 별도 모듈이다.

### 2. 흐름

| 동작 | 순서 |
|---|---|
| 첫 로드 | 실제 영역 → `dom_to_vdom`(기록함) → 기록 0번으로 저장 → a3로 코드 입력칸 → g1로 미리보기 (ADR-0006) |
| Patch | 코드 → g1 → 새 트리 → 미리보기 즉시 다시 그림 → `Diff(지금 트리, 새 트리)` → `changes`가 0개면 "변경 사항 없음"을 보여 주고 끝(k1) → 아니면 Patch → 지금 위치 뒤의 기록을 지우고(j1) 새 트리를 저장 → 버튼 상태 갱신 |
| 뒤로·앞으로가기 | 대상 기록 꺼냄 → `Diff(지금 트리, 대상 트리)` → Patch → 지금 위치 이동 → a3로 코드 입력칸 → g1로 미리보기 → 버튼 상태 갱신 |

- 뒤로·앞으로가기도 Diff·Patch로 실제 영역을 바꾼다. 통째로 다시 그리면 실제 영역의 입력값·스크롤이 사라진다(FR-04).
- 코드가 입력칸 값을 직접 바꾸면 사람이 타이핑할 때의 입력 신호가 생기지 않아 e3도 시작되지 않는 것으로 알고 있다. 그래서 미리보기 다시 그리기를 흐름에 명시한다.

### 3. 버튼 비활성화 (#26 + m3)

| 버튼 | 끄는 조건 |
|---|---|
| 뒤로가기 | 지금 위치가 0번 **또는** Patch하지 않은 수정이 있음 |
| 앞으로가기 | 지금 위치가 마지막 **또는** Patch하지 않은 수정이 있음 |

- **"Patch하지 않은 수정이 있다"의 기준**: 지금 코드로 만든 새 트리와 지금 트리를 Diff했을 때 `changes`가 0개가 아니면 수정이 있다. e3이 0.3초마다 만드는 새 트리를 재사용한다.
- 버튼이 꺼지면 상태 문구로 "Patch하거나 수정을 되돌리면 이동할 수 있습니다"를 보여 준다.
- **입력 직후 0.3초 사이의 틈 막기**: e3은 입력이 0.3초 멈춰야 새 트리를 만들므로, 그 사이에는 수정 여부를 판단할 수 없다. 그래서 코드 입력칸에 입력이 생기는 **즉시** 두 버튼을 끄고, 0.3초 뒤 새 트리로 위 기준을 판단해 다시 켤지 정한다. 들여쓰기만 바꾼 경우에도 버튼이 0.3초 동안 꺼졌다 켜지지만, 사용자가 알아채기 어려운 수준이다.

### Consequences

- Good, because 기록이 한 줄이라 앞으로가기의 뜻이 항상 하나로 정해지고, 버튼 비활성화 조건이 단순하다.
- Good, because 뒤로가기를 눌렀는데 화면이 안 바뀌는 칸이 생기지 않는다(k1).
- Good, because Patch하지 않은 수정을 실수로 잃지 않는다(m3).
- Good, because 뒤로·앞으로가기도 Diff·Patch를 거쳐 바뀌지 않은 요소의 입력값·스크롤이 유지된다.
- Bad, because 뒤로 간 뒤 새로 Patch하면 지워진 기록으로 다시 갈 수 없다(j1의 대가).
- Bad, because issue.md FR-07에 "변경 없는 Patch는 기록하지 않는다"는 예외가 생긴다(k1).
- Bad, because 수정 중에 고친 내용을 버리고 이동하려면 사용자가 코드를 직접 되돌려야 한다(m3).
- Neutral, because 입력 직후 버튼이 0.3초 동안 꺼졌다 켜질 수 있다.

## Pros and Cons of the Options

### 1. 분기

**j1. 지운다 (채택)**
- Good, because list + 지금 위치로 단순하고, 앞으로가기가 항상 하나로 정해진다.
- Good, because 브라우저 뒤로가기, 문서 편집기의 실행 취소와 같아 익숙하다.
- Bad, because 지운 기록으로 다시 갈 수 없다.

**j2. 남긴다**
- Good, because 아무 기록도 잃지 않는다.
- Bad, because 앞으로가기 규칙, 다른 갈래로 가는 화면, 기록 표시 방법을 새로 정해야 한다. 갈래로 가는 화면이 없으면 남긴 기록에 도달할 수 없다.
- Bad, because 자료구조가 트리가 되어 버튼 조건과 테스트가 늘어난다.

### 2. 변경 없는 Patch

**k1. 기록하지 않는다 (채택)**
- Good, because 같은 화면이 두 번 기록되지 않는다.
- Bad, because FR-07에 예외가 생긴다.

**k2. 기록한다**
- Good, because FR-07을 그대로 둔다.
- Bad, because 뒤로가기를 눌러도 화면이 안 바뀌는 칸이 생긴다.
- Bad, because j1 때문에 바뀐 것이 없는데도 앞쪽 기록을 잃는다.

### 3. Patch하지 않은 수정

**m1. 그냥 덮어쓴다**
- Good, because 새로 정할 것이 없다.
- Bad, because 실수로 누르면 고친 내용을 잃는다.

**m2. 확인을 받는다**
- Good, because 고친 내용을 버리고 이동하는 선택지를 남긴다.
- Bad, because 확인 화면, 확인을 기다리는 동안의 조작 규칙, 수정 여부 판단 기준이 모두 필요하다. 브라우저 기본 확인 창은 페이지를 멈추게 해 자동 테스트에 가짜 함수가 필요하다.

**m3. 버튼을 끈다 (채택)**
- Good, because 실수로 잃는 일 자체가 없다.
- Good, because 판단 기준이 k1과 같고, e3의 새 트리를 재사용한다.
- Bad, because #26 버튼 조건이 하나 늘어나고, 입력 직후 틈을 막는 규칙이 필요하다.

## More Information

### 확장 후보: 잘린 기록 백업 (`archive[]`)

PR #50에서 팀원이 j1의 대가("지운 기록으로 다시 갈 수 없음")를 보완하려고, 지우는 기록을 별도 배열 `archive[]`(최대 50개)에 보관하고 복구하는 기능을 제안했다. 메인 기록은 한 줄로 유지되어 이 ADR의 다른 결정과 충돌하지 않는다. 다만 다음 이유로 **이번에는 채택하지 않고 확장 후보로 남긴다.**

- 보관된 기록을 보여 주고 고르는 화면이 설계에 없다. 만들면 j2를 고르지 않은 이유인 "다른 갈래로 가는 방법"과 같은 비용이 든다.
- 기록 중간에서 복구할 때의 동작(뒤 기록 처리, 지금 위치 이동, 실제 영역 Patch, m3와의 관계)이 정해지지 않았다.
- 여러 번 잘린 기록이 한 줄로 섞여 원래 흐름(B 다음 C)이 사라진다.
- 최대 50개를 넘으면 버리므로 "100% 복구"가 아니다.
- 요구사항 밖이고 마감까지 여유가 없다.

나중에 붙일 때는 위의 처음 세 가지(보관 기록을 고르는 화면, 복구 동작, 잘린 묶음 단위 보관)를 먼저 설계한다. j1 위에 더하는 구조라 History 모듈 밖은 바뀌지 않는다.
