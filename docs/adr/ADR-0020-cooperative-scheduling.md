# ADR-0020: Diff를 노드 단위 작업으로 바꿔 시간 분할(협력적 스케줄링)로 실행할 수 있게 하고, Commit은 동기로 둔다. 효과는 성능 실험실에서 측정해 보여 준다

## Context and Problem Statement

우리 미니 React는 렌더링을 동기로 끝까지 실행한다. 작업량이 많으면 JavaScript 메인 스레드를 오래 점유해, 그동안 사용자 입력이 늦게 반영된다(메인 스레드 점유 문제). jsdom에서 잰 값은 다음과 같다(목록 항목마다 노드 3개).

| 목록 크기 | Diff | Patch(Commit) |
|---|---|---|
| 1,000개 | 약 6ms | 약 5ms |
| 10,000개 | 약 43ms | 약 57ms |

1,000개는 Long Task(50ms) 기준에 한참 못 미치지만, 10,000개부터는 Diff와 Commit 각각이 기준에 가까워진다. 실제 React는 렌더 단계를 작은 작업으로 나눠 사이사이 메인 스레드를 양보한다(Fiber). 우리는 무엇을, 어디까지 나눌까?

## Decision Drivers

- 같은 입력에 대해 결과(변경 목록)가 동기 Diff와 **항상 같아야** 한다.
- 이미 검증된 Diff·Patch(테스트 191개, ADR-0004·0005)를 흔들지 않는다.
- 효과는 "빠르다"는 주장이 아니라 측정값으로 보여 주고, 자동 테스트는 기계마다 같은 값(결과·노드 수)으로 판정한다(SDD 11장 9번 결정).
- Virtual DOM이 만능이 아니라는 점을 숨기지 않는다.

## Considered Options

- **o1. 하지 않는다**: 한계로만 설명한다.
- **o2. Diff를 별도로 다시 짠다**: 재귀 Diff와 따로, 명시적 스택을 쓰는 반복 Diff를 새로 만든다.
- **o3. 같은 Diff 코드를 작업 단위(generator)로 바꾼다**: 노드 하나를 처리할 때마다 멈출 수 있게 하고, 동기 `diff()`는 끝까지 한 번에, `diffSliced()`는 시간을 나눠 돌린다.
- **o4. 렌더 단계 전체를 나눈다**: 컴포넌트 함수 실행까지 나눈다(Fiber에 가까움).

## Decision Outcome

Chosen option: **o3** (제안).

- o2보다 나은 이유: 두 Diff가 같은 코드라 결과가 갈라질 수 없다. 기존 Diff 테스트 전부가 그대로 새 구조를 검증한다.
- o4를 택하지 않은 이유: `h()`가 자식 컴포넌트를 바로 펼치므로(ADR-0015 1절) 렌더 단계에 나눌 지점이 없다. 바꾸려면 ADR-0015를 다시 열어야 한다.

### 1. 작업 단위와 스케줄러

| 구성 | 구현 |
|---|---|
| 작업 단위 | `diffSteps()`: Diff가 노드 하나를 볼 때마다 멈출 수 있는 generator. `diff()`는 이것을 끝까지 돌린다 |
| 스케줄러 | `diffSliced(old, new, { budgetMs = 5 })`: 한 조각에서 정해진 시간 동안만 노드를 처리한다. 최소 1개는 처리해 반드시 앞으로 간다 |
| 양보와 재개 | 시간이 다 되면 `MessageChannel`(없으면 `setTimeout 0`)로 다음 조각을 예약하고 돌려준다. 다음 조각은 멈춘 노드부터 이어서 한다 |
| 취소 | `cancel()`하면 `done`이 `null`로 끝나고 더 예약하지 않는다. 새 업데이트가 오면 앞의 작업을 버리고 최신 상태로 다시 시작한다 |
| Commit | **나누지 않는다.** `done` 뒤에 `applyPatch`를 한 번에 부른다. 실제 DOM을 반쯤만 바꾼 상태를 사용자에게 보이지 않기 위해서다 |

### 2. 성능 실험실 (`pages/lab`, TBD-12·TBD-14)

같은 목록 변경(항목 1,000·10,000·30,000개, 1개만 또는 전부 변경)을 세 방식으로 적용해 나란히 보여 준다.

| 방식 | 내용 |
|---|---|
| Patch (동기) | 지금 엔진 그대로 |
| Patch (협력적 스케줄링) | `diffSliced` → Commit 한 번 |
| 통째 교체 | Diff 없이 목록을 새로 만든다 (`innerHTML`과 같은 방식) |

**바로 고치기(Signals, 비교 없애기)**: 값(signal)과 그 값을 쓰는 화면 칸(effect)의 연결을 처음에 기억해 두고, 값이 바뀌면 그 칸만 고친다. Diff가 없다. Svelte·Solid·Vue의 방식을 작은 별도 데모로 보여 줄 뿐, 우리 엔진은 바꾸지 않는다.

**보이는 만큼만(가상 스크롤, 비교 줄이기)**: 상품 10만 개 중 화면에 보이는 줄만 Virtual DOM으로 만들고, 스크롤하면 그 줄들만 기존 `diff`·`applyPatch`로 고친다(기존 설계·구현 변경 없음). 비교 비용을 줄이는 대표 방법을 보여 준다.

보여 주는 값: 메인 스레드 최장 연속 점유(Long Task 50ms 기준), Diff·Commit 시간, 조각 수, DOM 수정·생성·제거 노드 수(`MutationObserver`), 입력 지연(`input` 이벤트 시각부터 처리까지), 브라우저가 기록한 Long Task 수(`PerformanceObserver`, 지원 브라우저만).

### 3. 알려진 한계

- Commit은 동기라, 바뀐 노드가 많으면(10,000개 전부 변경) 여전히 Long Task가 생길 수 있다. 이 경우는 DOM 변경량 자체를 줄여야 한다.
- 나눠서 실행하면 양보와 예약 비용 때문에 전체 시간은 늘어난다.
- 전부 바뀌는 변경에서는 Patch도 모든 노드를 고쳐야 해서 통째 교체와 큰 차이가 없을 수 있다(Virtual DOM은 만능이 아님).
- Phase 2 `FunctionComponent.update()`는 아직 동기 `diff`를 쓴다. 적용 여부는 실험 결과를 보고 따로 정한다.

### Consequences

- Good, because 큰 목록에서 Diff 동안 메인 스레드를 잡는 시간을 조각 하나(약 5ms)로 줄인다.
- Good, because 결과가 동기 Diff와 같다는 것을 무작위 입력 테스트로 증명한다.
- Good, because 측정과 한계를 함께 보여 주어 발표에서 방어하기 쉽다.
- Bad, because generator 때문에 동기 Diff도 약간 느려질 수 있다(테스트 191개와 1,000겹 중첩은 그대로 통과).
- Bad, because 비동기 흐름(취소, 최신 상태)이 생겨 페이지 코드가 복잡해진다.
