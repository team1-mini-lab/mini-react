# ADR-0008: History는 선형 기록으로 관리하고, 변경 없는 Patch는 기록하지 않으며, Patch하지 않은 수정이 있으면 이동 버튼을 끈다

> **개정 내역**: 최초안은 결정 1(분기 시 이후 기록 삭제)만 다뤘다. 팀 설계 검토([블로그 97](https://eutopiaa.tistory.com/97))에서 결정 2·3·4가 추가되었고, `dom` 규칙과 충돌하던 문장 하나를 고쳤다.

## Context and Problem Statement

Phase 1 검증 페이지는 Patch할 때마다 그 시점의 Virtual DOM을 State History에 저장하고(FR-07), 뒤로가기·앞으로가기로 이동한다(FR-08). 다음 네 가지를 정해야 한다.

1. 뒤로 간 상태에서 새로 Patch하면 그 뒤의 기록은 어떻게 하나? (SRS TBD-01)
2. 바뀐 것이 없는 Patch도 기록하나?
3. 코드 입력칸에 Patch하지 않은 수정이 있을 때 뒤로·앞으로가기를 누르면 어떻게 하나?
4. 입력 직후, 수정 여부를 판단하기 전 0.3초(ADR-0006 e3) 사이의 틈은 어떻게 하나?

예시: 첫 로드 → A, Patch 1 → B, Patch 2 → C (지금 C).

## Decision Drivers

- 앞으로가기 동작이 사용자에게 예측 가능한가
- 사용자가 고친 내용이나 기록을 실수로 잃지 않는가
- 자료구조와 버튼 상태 계산이 단순한가
- 과제 원문("이전 또는 다음 시점으로 이동")의 범위와 일정
- ADR-0004 `dom` 규칙, ADR-0006 흐름과의 일관성

## Considered Options

**결정 1. 분기 후 기록**
- j1. B, C를 지운다 (선형)
- j2. B, C를 남긴다 (트리, 갈래 선택 UI 필요)
- j3. 잘린 기록을 별도 백업 배열에 보관한다 (선형 + `archive[]`)

**결정 2. 변경 없는 Patch**
- k1. 기록하지 않고 "변경 사항 없음"을 알린다
- k2. 기록한다

**결정 3. Patch하지 않은 수정이 있을 때 이동**
- m1. 그냥 덮어쓴다
- m2. 확인을 받는다
- m3. 수정이 있으면 이동 버튼을 끈다

**결정 4. 판단 전 0.3초의 틈**
- n1. 그대로 둔다 (판단 전에는 버튼이 켜져 있음)
- n2. 입력 즉시 두 버튼을 끄고, 0.3초 뒤 판단해서 다시 켤지 정한다

## Decision Outcome

Chosen options: **j1, k1, m3, n2**.

- **j1**, because 브라우저 뒤로가기·문서 편집기와 같은 동작이라 앞으로가기가 항상 하나로 정해지고, 기록이 배열 하나 + 위치 번호 하나로 끝나며, 과제 원문이 "이전 또는 다음 시점으로 이동"만 요구하기 때문이다. j2·j3는 일정상 범위 밖으로 두되, 확장은 History 모듈 안에서 끝나고 Diff·Patch는 건드리지 않는다.
- **k1**, because 기록하면 첫 뒤로가기가 B → B라 화면이 안 바뀌어 버튼이 고장 난 것처럼 보이고, j1에 따라 바뀐 것도 없는데 앞으로가기 기록(C)을 잃기 때문이다.
- **m3**, because m1과 달리 고친 내용을 잃는 일 자체를 막고, m2와 달리 확인 화면과 그동안의 조작 규칙이 필요 없기 때문이다.
- **n2**, because n1이면 입력 직후 0.3초 안에 누른 뒤로가기가 m3로 막으려던 일을 그대로 일으키기 때문이다. 들여쓰기만 바꿔도 버튼이 0.3초 꺼졌다 켜지지만 알아채기 어려운 수준이다.

### 1. 기록 구조

| 규칙 | 이유 |
|---|---|
| 첫 로드 상태를 0번 기록으로 둔다. Patch n번(변경 있음) → 기록 n + 1개 | 0번이 없으면 처음 샘플 화면으로 돌아갈 수 없다. FR-07 "n개 **늘어난다**"와 맞다 |
| 뒤로 간 상태에서 Patch하면 지금 위치 뒤의 기록을 지우고 추가한다 (j1) | 결정 1 |
| 기록 한도(100)를 넘으면 가장 오래된 기록부터 버린다 | 메모리 상한 |
| `canUndo()` = 지금 위치 > 0, `canRedo()` = 지금 위치 < 마지막 | 버튼 비활성화(#26), FR-08 "처음·끝에서는 아무 일도 없다"를 눈에 보이게 지킨다 |

### 2. 변경 판단 (k1, m3 공통)

"바뀐 것이 있는가"는 **`diff(지금 트리, 코드로 만든 새 트리).changes`가 0개인가**로 판단한다.

- 들여쓰기만 바꾼 코드는 공백 규칙(ADR-0002)으로 같은 트리가 되므로 수정 없음이다.
- `key`만 바꾼 코드는 다섯 키 비교로는 같지만 Diff는 삭제 + 추가를 만든다(ADR-0004). Diff로 판단해야 이 경우를 "수정 있음"으로 잡는다. 다섯 키 비교(FR-01 비교 기준)를 쓰지 않는 이유다.
- 새 트리는 e3이 미리보기를 위해 이미 만들므로 추가 비용은 Diff 한 번이다. Diff는 실제 DOM을 건드리지 않는다.

### 3. 이동 흐름

```
뒤로가기:  target = history.undo()
          → Diff(지금 트리, target) → Patch         ← '이전'은 언제나 지금 트리 (ADR-0004 dom 규칙 7)
          → 코드 입력칸 ← target을 코드로 (ADR-0006 a3)
          → 미리보기 ← 코드를 다시 읽어 그림 (ADR-0006 g1)
          → 버튼 상태 다시 계산
```

- 변경이 0개여도 Patch를 부른다. 짝 목록(`pairs`)대로 `dom`을 `target`에 이어 줘야 다음 Patch가 동작하기 때문이다(ADR-0005).

### 4. 저장된 기록과 `dom`

최초안의 "History에 저장된 객체를 수정하지 않는다"를 다음으로 고친다.

> History에 저장된 트리의 **화면 데이터(다섯 키)와 `key`**는 수정하지 않는다. `dom`은 Patch만 쓰며, 지금 실제 영역에 그려진 트리에서만 믿는다(ADR-0004 `dom` 규칙 7).

뒤로가기를 하면 기록 B가 Diff의 "새 트리"가 되어 Patch가 B의 객체들에 `dom`을 써 넣는다. B가 지금 트리가 되는 순간 B의 `dom`이 정확해지는 것이므로 맞는 동작이다. 같은 이유로 History에는 Patch가 `dom`을 채운 **바로 그 트리 객체**를 넣는다. 복사본을 넣으면 다음 Diff의 "이전" 쪽에 `dom`이 없다.

### Consequences

- Good, because History가 배열 + 위치 번호만으로 구현되고, 버튼 상태가 위치와 수정 여부 두 가지로 정해진다.
- Good, because 사용자가 고친 내용(m3·n2)도, 앞으로가기 기록(k1)도 실수로 잃지 않는다.
- Good, because k1과 m3가 같은 판단 기준(Diff 변경 0개)을 쓴다.
- Bad, because 분기 이전의 B, C는 되살릴 수 없다(j1).
- Bad, because 수정 중에는 버튼이 꺼지므로, 고친 내용을 버리고 이동하려면 코드를 되돌리거나 Patch해야 한다. 버튼이 꺼진 이유를 안내 문구로 알린다.
- Neutral, because 들여쓰기만 바꿔도 버튼이 0.3초 꺼졌다 켜진다.

### Confirmation

- `history.test.ts`: A, B, C push → undo 2회 → D push 후 `size === 2`(A, D), `canRedo() === false` (j1).
- `history.test.ts`: push n회 → undo n회 → 초기 상태, redo n회 → 마지막 상태.
- `phase1.test.ts`: 고치지 않고 Patch → 기록 수 그대로, "변경 사항 없음" 표시. [A, B, C]에서 B로 돌아와 고치지 않고 Patch해도 C가 남는다 (k1, SRS VT-47).
- `phase1.test.ts` (가짜 타이머): 입력 직후 두 버튼이 꺼진다. 0.3초 뒤 들여쓰기만 바꾼 경우 다시 켜지고, 글자나 `key`를 바꾼 경우 꺼진 채 안내 문구가 보인다 (m3, n2, SRS VT-48).
- `phase1.test.ts`: 뒤로가기 후 미리보기와 기록이 FR-01 비교 기준으로 같다 (SRS VT-49).

## Pros and Cons of the Options

### 결정 1

- **j1 (채택)**: Good, 구현·테스트가 가장 단순하고 익숙한 동작. Bad, 버려진 기록을 되살릴 수 없다.
- **j2 트리**: Good, 어떤 기록도 잃지 않는다. Bad, 갈래 선택 UI가 필요하고 앞으로가기의 의미가 모호해지며 과제 범위를 넘는다.
- **j3 `archive[]`**: Good, 메인 기록은 선형을 유지하면서 잘린 기록을 복구할 수 있다(SDD v0.4 제안, PR #50). Bad, 복구 UI와 복구한 기록을 어디에 둘지 규칙이 더 필요하다. 확장 후보로 남긴다(SDD 부록 C).

### 결정 2

- **k1 (채택)**: Good, 뒤로가기가 한 번에 의미 있게 움직이고 앞으로가기 기록을 잃지 않는다. Bad, FR-07 인수 기준에 예외 문구를 더해야 한다.
- **k2**: Good, "Patch n번 = 기록 n개"가 예외 없이 성립한다. Bad, 화면이 안 바뀌는 뒤로가기가 생기고 앞으로가기 기록을 잃는다.

### 결정 3

- **m1**: Good, 정할 것이 없다. Bad, 실수로 누르면 작업을 잃는다.
- **m2**: Good, 실수를 막는다. Bad, 확인 문구 위치와 기다리는 동안의 조작 규칙이 필요하고, 브라우저 `confirm`은 자동 테스트를 어렵게 한다.
- **m3 (채택)**: Good, 실수가 아예 불가능하다. Bad, 끄는 이유를 안내해야 한다.

### 결정 4

- **n1**: Good, 추가 코드가 없다. Bad, 0.3초 안의 클릭으로 m3가 무력해진다.
- **n2 (채택)**: Good, 틈이 없다. Neutral, 들여쓰기만 바꿔도 잠깐 꺼진다.
