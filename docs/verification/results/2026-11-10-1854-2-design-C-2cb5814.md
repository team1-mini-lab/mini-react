### 3. 팀이 결정해야 할 것

**1. [SDD Phase1 11.2] `t3` 복구 시점의 원자성 보장 방식**
- 선택지 1: **전체 렌더링(Full Re-render)** - 현재 `history.dom`을 기준으로 컨테이너의 `innerHTML`을 비우고 새로 그림.
    - 대가: 상태(input focus 등)가 소실되고 성능 비용이 큼.
- 선택지 2: **체크포인트 DOM 보관** - 패치 시작 전 `cloneNode(true)`로 DOM 스냅샷을 메모리에 들고 있다가 실패 시 교체.
    - 대가: 메모리 사용량이 일시적으로 2배가 됨.

**2. [SDD Phase1 11.3] `recordDom` 인덱스 유효성 문제**
- 선택지 1: **역순 적용(Reverse Iteration)** - `REMOVE` 작업 등을 뒤에서부터 수행하여 인덱스 변화 영향을 최소화함.
    - 대가: `INSERT`와 혼합된 복잡한 이동(Move) 로직에서 알고리즘 복잡도가 급증함.
- 선택지 2: **ID/Path 기반 참조** - 인덱스 대신 `data-path="0.1.2"` 같은 경로를 사용해 노드를 탐색.
    - 대가: 매 패치마다 DOM 탐색 비용이 발생하며, HTML 구조 변경 시 Path도 갱신되어야 함.

**3. [SDD Phase2 7.1] Batching 중 발생하는 에러 처리**
- 선택지 1: **전체 취소(Rollback)** - 해당 배치에 포함된 모든 컴포넌트 업데이트를 무효화하고 이전 안정 상태로 복구.
    - 대가: 한 컴포넌트의 에러가 무관한 다른 컴포넌트의 업데이트까지 막음.
- 선택지 2: **부분 적용(Partial Update)** - 에러가 난 컴포넌트만 무시하고 나머지는 반영.
    - 대가: 컴포넌트 간 데이터 의존성이 있을 경우 전체 트리의 일관성이 깨질 위험이 있음.
