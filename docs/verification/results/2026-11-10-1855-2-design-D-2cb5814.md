# Analyzing Findings for Area D (History & Page)

Based on the documentation:
- **History (ADR-0008):** Uses a stack-based approach for Undo/Redo. Each entry stores a "Snapshot" (vNode tree).
- **Dirty State (SDD P1 7.2):** `isDirty` is true when the editor content differs from the "Current" (applied) state.
- **Pending Changes:** Changes waiting to be applied via the "Apply" button.
- **Undo/Redo Logic:** SDD 6.3 describes moving the pointer.
- **SDD P1 Section 11.2:** Mentions "State Sync between Editor and History during Undo".

## Scenario 1: Undo during a Dirty State
1. User edits text (State: `isDirty=true`, `pendingChanges` exist).
2. User clicks Undo.
3. Does the editor revert to the previous history state, or does it just clear the `dirty` state?
4. SDD 6.3 says Undo moves the pointer in the History Stack. ADR-0008 says History stores "Applied" snapshots.
5. **Conflict:** If History only stores "Applied" states, an Undo while `isDirty=true` might lose the current unapplied edits without a way to Redo them (since they were never "Applied" to the stack).

## Scenario 2: Rapid Undo/Redo and DOM Sync
1. ADR-0008 Section 4.2: Undo/Redo triggers `vnodeToHtml` and replaces the editor content.
2. If the user is mid-typing or an async operation (Phase 2 batching) is pending, could the pointer move while the DOM is still rendering?

## Scenario 3: Initial State Undo
1. Initial Load. Stack: `[S0]`, Pointer: 0.
2. Undo button should be disabled.
3. SRS VT-401 requires Undo button to be disabled at the start.

### 3. Team Decisions Required

1. **SDD P1 11.2: History vs Dirty Interaction**
   - **Option A:** Undo first reverts the editor to the last "Applied" state (clears `isDirty`), then the next Undo moves the history pointer.
     - *Cost:* Extra click for users; `isDirty` acts as a "pseudo-history" entry.
   - **Option B:** Undo immediately moves the history pointer and discards unapplied edits.
     - *Cost:* Potential data loss if the user accidentally clicks Undo while typing.

2. **Phase 2 7.1: Component State Preservation during Undo**
   - **Option A:** Re-mount everything from HTML (Reset state).
     - *Cost:* Lost input focus, scroll position, and local component state (Phase 2 hooks).
   - **Option B:** Reconciliation (Diff) between current DOM and History VNode.
     - *Cost:* High complexity in the Patch engine; must ensure History VNodes are "clean".

3. **Phase 2 7.2: Batching and History**
   - **Option A:** Each "Apply" click is one History entry, regardless of how many batched renders happened.
     - *Cost:* Simple but coarse-grained.
   - **Option B:** Every state change (even batched) creates a history entry.
     - *Cost:* Floods history with micro-steps; inconsistent with "Apply" button requirement.

### 3. 팀이 결정해야 할 것

1. **SDD P1 11.2: Dirty 상태와 Undo의 우선순위**
   - **선택지 1:** Undo 클릭 시 Dirty한 변경사항을 먼저 버리고(Apply 전 상태로 복귀), 한 번 더 눌러야 History를 뒤로 돌림.
     - *대가:* 사용자가 직전 편집을 취소하기 위해 Undo를 두 번 눌러야 할 수 있음.
   - **선택지 2:** Undo 시 Dirty 여부와 상관없이 즉시 History Pointer를 이동하고 Dirty 변경사항은 폐기함.
     - *대가:* 실수로 Undo를 눌렀을 때 적용하지 않은 편집 내용이 영구 소실됨(Redo로 복구 불가).

2. **Phase 2 7.1: Undo/Redo 시 컴포넌트 상태(Hooks) 유지 여부**
   - **선택지 1:** `vnodeToHtml`로 전체를 다시 그려서 초기화함.
     - *대가:* 입력창 포커스, 스크롤 위치, `useState`로 관리하던 로컬 UI 상태가 모두 날아감.
   - **선택지 2:** History의 VNode와 현재 DOM을 Diff/Patch하여 변경분만 적용함.
     - *대가:* Patch 엔진이 History 복구 모드를 지원해야 하며, VNode 스냅샷의 무결성 관리가 복잡해짐.

3. **Phase 2 7.2: 배치(Batching) 작업 중 History 조작 차단**
   - **선택지 1:** 상태 업데이트가 배치 처리 중일 때는 Undo/Redo 버튼을 비활성화함.
     - *대가:* 매우 빈번한 업데이트 시 버튼이 깜빡거리거나 조작이 답답할 수 있음.
   - **선택지 2:** 배치와 상관없이 Pointer를 이동하고, 다음 렌더링 사이클에서 History 상태를 강제 반영함.
     - *대가:* 비동기 렌더링 결과와 History 상태가 꼬일 위험이 있음.
