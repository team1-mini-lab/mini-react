성능 실험실

React가 왜 필요한지, 각 설계가 어떤 문제를 해결하는지 같은 화면에서 직접 실험해 봅니다. 숫자뿐 아니라 구현 복잡도, 추가 비용, 사용자 경험의 장단점도 함께 봅니다.

같은 목록 변경을 세 방식으로 적용해 봅니다. 협력적 스케줄링은 Diff를 5ms씩 나눠 실행하고 사이사이 메인 스레드를 양보해서, 큰 목록을 처리하는 동안에도 입력이 막히지 않게 합니다. 실제 DOM에 반영하는 Commit은 나누지 않습니다.

입력 지연이 여기에 표시됩니다

버튼을 눌러 실행하세요
읽는 법
  • 최장 연속 점유가 50ms를 넘으면 그동안 클릭·입력을 처리하지 못합니다(Long Task).
  • 10,000개 이상에서 동기 Patch는 Diff 동안 메인 스레드를 오래 잡습니다. 협력적 스케줄링은 Diff를 잘게 나눠 이 시간을 줄이지만, 전체 시간은 조금 늘어납니다.
  • Commit(실제 DOM 반영)은 나눌 수 없어서, 바뀐 노드가 많으면 여전히 길 수 있습니다. 그래서 DOM 변경량 자체를 줄이는 것이 중요합니다.
  • 전부 변경이면 Patch도 노드를 모두 고쳐야 해서 통째 교체와 큰 차이가 없을 수 있습니다. 1개만 변경에서 차이가 분명합니다. Virtual DOM은 만능이 아닙니다.
  • 시간은 기계와 브라우저마다 다릅니다. 자동 테스트는 노드 수와 결과 화면으로만 판정합니다.

실험 1 · DOM 업데이트: Patch vs 통째 교체

방식에서 "Patch (동기)"와 "통째 교체"를 고르고, 변경 범위를 바꿔 가며 비교해 보세요.

Patch (Virtual DOM + Diff)통째 교체 (innerHTML)
실행 시간바뀐 게 적을수록 Commit이 짧음. 대신 Diff가 트리 전체를 훑는 비용이 항상 듦Diff가 없어 단순하지만, 매번 노드를 전부 새로 만듦
DOM 조작1개 변경 → 수정 11개 변경이어도 노드 수만큼 새로 만들고 떼어 냄
사용자 경험입력값·커서·스크롤·포커스가 유지됨입력 중이던 값과 포커스, 스크롤이 사라짐
구현 복잡도높음: 변환, Diff 6종, key 짝짓기, 적용 순서, 실패 복구낮음: 문자열 한 줄
추가 비용Virtual DOM 트리를 메모리에 두고 비교하는 비용없음
언제 유리한가일부만 자주 바뀌는 화면 (대부분의 앱)전부 바뀌는 화면, 한 번 그리고 끝나는 화면

실험 3 · 협력적 스케줄링: 동기 렌더링 vs 시간 분할

항목 10,000개로 바꾸고 "3초 동안 계속 업데이트"를 누른 뒤 입력칸에 타이핑해 보세요. 동기와 협력적 스케줄링에서 입력 지연을 비교합니다.

동기 렌더링 (지금 엔진)협력적 스케줄링 (Diff 시간 분할)
메인 스레드 점유Diff + Commit을 한 번에. 10,000개에서 50ms를 넘기 쉬움 (Long Task)Diff는 5ms 조각으로 나누고 사이사이 양보. 가장 긴 구간은 Commit
전체 시간가장 짧음양보·예약 비용 때문에 더 김
사용자 경험업데이트 중 입력·클릭이 늦게 반영될 수 있음업데이트 중에도 입력이 바로 처리됨
구현 복잡도낮음: 함수 호출 한 번높음: 멈추고 이어 하기, 취소, 최신 상태 우선, 비동기 흐름
결과 정확성기준같은 Diff 코드를 쓰므로 결과가 항상 같음 (무작위 300쌍 테스트)
